# 插件故障登记规程

> 本文件规定**什么时候往这里写、怎么写**。故障正文在 [`pitfalls.md`](./pitfalls.md)。

## 一条铁律

**凡是 DSH 插件类故障，一律登记到 `references/pitfalls.md` 的第 5 节。**
包括但不限于：插件加载失败、面板显示异常、服务注入失败、工具注册失败、配置校验失败、构建产物缺失、依赖遮蔽宿主、安装/升级/回滚异常。

登记前先问三件事：

1. **是不是已经有一条覆盖它？** 按「症状」找，不按插件名找。已有就补充到那一条，不新开。
2. **能不能拿到原始报错文本？** 能，就贴原文——这是唯一可靠的分诊依据（见 pitfalls 5.10 结尾）。
3. **这条结论是实测还是推测？** 只有实测才写进第 5 节。推测标注清楚，或先别写。

## 新增一条的写法

第 5 节每条按**故障模式**组织，不绑具体插件。模板：

```markdown
### 5.N <一句话命名：症状 + 根因>

**症状**：面板/日志上**能直接看到**的表现。贴原始报错文本，不要转述。

```
<原始日志或弹窗文字>
```

**故障模式**：为什么会这样。用最小代码片段说明错误写法与正确写法。

```ts
// ✗ 错误
// ✓ 正确
```

**判断步骤**：一段可直接执行的命令（PowerShell 或 Node），用来确认是不是这一条。

```powershell
# 或 ```js
```

**规则**：

- 给读者可执行的行动项，不给「要注意」这种空话
- 与其他小节的**区分方法**要写清楚（同类症状最容易互相误判）
- 若涉及「改了配置但没生效」，务必写明**是否需要完全重启 DSH**
```

## 命名的硬约束

| 约束 | 原因 |
|---|---|
| 不写插件名，用 `<包名>` / `<id>` | 故障模式跨插件复用 |
| 症状用**原文报错**，不转述 | `reading 'validate'` 与 `pending` 是完全不同的两条 |
| 编号连续，插入时重排 | 5.1–5.11 已按出现顺序排列，保持可引用 |
| 每节独立可读 | 读者可能只搜到某一节 |
